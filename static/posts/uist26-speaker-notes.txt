Slide 6 — Place & Time — Calculator

Step 1

If we think of debugging as querying a program's execution, then it's helpful to have a way to talk about the structure of execution data.

We visualize this using the orthogonal axes of Place and Time

Place refers to all of the locations in the code and the variables contained there. You can kind of imagine lines of source code  mapping to vertical positions.

Time, as you might expect, refers to the progression of execution, with things that happen later in execution appearing rightwards on the axis.

Slide 7 — Place & Time — Print debugging

Step 1

We can use the Place-Time chart to understand what different debugging tools are doing for us.

After I add a print statement to my code, when that line of code executes, it prints the expressions that I queried for.

This happens every time the print statement executes, and the fact that it does is what makes print debugging so useful. I log a particular Place in the code, and the query that I'm expressing is "show me this place across all time".

Slide 8 — Place & Time — Breakpoint debugging

Step 1

A breakpoint basically gives me a query across the other axis: when I'm paused on a breakpoint, I can see across all currently relevant places at this particular moment in time.

When I advance the debugger by stepping, I'm getting a different slice of all places at the new point in time. So the value in breakpoints is that I have quick, interactive access across places.

Slide 16 — Transformations

Step 1

Participants didn't just issue one query. We saw them issue multiple queries over the course of a session, oftentimes modifying their existing queries. We call these transformations or movements in place-time.

Step 2

The most common one by far was widening across place. This looks something like adding new variables to a print statement. Doing this gives more context for the current line of investigation.

Step 3

Again, if you're working on a debugging tool, you should think about how it supports transformations. What does the interaction look like?

Step 4

There was another common transformation: narrowing in time. For print, this looks like wrapping your print line in a condition. I think it's interesting that participants did this, because it's technically strictly less information, and I think it speaks to there being a cost to having too much stuff to look at.

---

Slide 17

Step 1

Narrowing in time corroborates something we saw in our formative interviews: industry software engineers engaged in what we call Pre-Filtering, 

Step 2

where they intentionally did not query for information that they thought could be useful, because they were afraid of producing more output than they could handle. They intentionally restricted their queries.

Step 3

For example, a print user said "there will be a lot of statements, right? it looks like too much information for me to look at and process and get an output".

This, to me, smells like a limitation of the tools. For fear of flooding the terminal with too much output, programmers intentionally query for less. Isn't that wrong? Because the tool can't help them, they intentionally inhibit their own comprehension process.

Slide 24 — autopsy — Across Place & Time

Step 1

I think that Data-Oriented Debugging points towards a tool that makes it easy to express many different types of queries with the same tool, since we saw in our study that programmers issue multiple different query shapes in a single debugging session. I've been working on a tool like this that I call "autopsy"

Step 2

Using autopsy initially looks like using print debugging. You add these log calls to your code

Step 3

When a particular log call executes, it logs the expression you gave it. But it also takes a snapshot that gives you a view across all place at the time of the log

Step 4

This means if you wanted to, say, also see the values of left and right at this time, you can do that by interacting with the log output

Step 5

And since log otherwise behaves like a normal print line, we can do this across time

Step 6

Also, we capture these snapshots as actual data and not strings, which means we can compute further information from them

Step 7

A simple example is you could compute summary statistics about a numeric variable
